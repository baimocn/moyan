## 二、【结构化输出方案】对比与墨衍推荐

### 2.1 方案对比（Python + FastAPI 视角）

| 方案 | 原理 | FastAPI 集成方式 | 可靠性等级 | 关键事实（来源） |
|---|---|---|---|---|
| **纯 JSON mode**（`response_format: {"type":"json_object"}`） | 软约束：提示词带"json"+ 示例，SDK 层保证输出可解析为 JSON 串 | openai SDK `chat.completions.create(..., response_format=...)`，返回后 `json.loads` + Pydantic 校验 | ★★☆ 只保证"是 JSON"，**不保证字段符合 schema** | DeepSeek 官方文档原文（已抓取）：需设置 `response_format={'type':'json_object'}`；prompt 中必须含"json"字样；**要给它 JSON 格式示例**；**合理设置 max_tokens 防止 JSON 被截断** |
| **OpenAI Strict Structured Outputs**（`json_schema` + `strict: true`） | 硬约束（服务端解码器）："ensures the model will match your supplied JSON schema" | openai SDK 直接支持；instructor/自己封装皆可 | ★★★★ 官方保证 schema 匹配；注意**strict 下只支持 JSON Schema 子集**；需 `additionalProperties:false`、字段全必填 | 已从 openai-python SDK 源码 docstring 核实（`completion_create_params.py`、`response_format_json_schema.py`）；`platform.openai.com` 本网络不可达，细节以官方文档为准 |
| **Function / tool calling**（把"判定"定义成工具参数） | 软约束 + 结构化：模型输出 `tool_calls[].arguments`（JSON），OpenAI/Claude/DeepSeek 原生兼容 | SDK 的 `tools=[{type:"function", function:{...}}]`，解析 `message.tool_calls` | ★★★☆ 比 json_object 字段更可靠，但模型仍可能抛错/不调工具 → 仍要校验 + 重试 | DeepSeek 官方文档含 Tool Calls 专节（导航已见，页面标题可证实）；NexusRaven/BFCL 即此场景评测 |
| **instructor**（Pydantic + 自动 reask） | 在 provider 之上统一做：schema 注入 + **失败自动带错误重试** + 流式 | `response_model=JudgeResult`，内部按 provider 自动选 function calling / json mode | ★★★★ 开箱即用，把"校验失败→重试"做成框架能力；README 明示对比裸 JSON mode 的优势 | instructor README 直接抓取核实 |
| **outlines / lm-format-enforcer / llguidance**（本地受限解码） | **生成期硬约束**：Schema→FSM→逐 token 屏蔽非法输出，保证合法 JSON | 只能接本地/自托管推理（transformers/vLLM/llama.cpp） | ★★★★★ 语法级保证；但对**云端 API 模型无效** | outlines README：Guaranteed valid structure；lm-format-enforcer README 能力表 |
| **guardrails** | 后置防线：validator 校验 → 修复/重试 | 包一层在调用链外，与 FastAPI 解耦 | ★★★☆ 补漏网之鱼（如语气、敏感、边界条件） | guardrails README 直接抓取核实 |

**可靠性总结**：`本地受限解码(硬) > OpenAI Strict json_schema(硬) ≈ function calling + 校验重试(软+兜底) > json_object + 校验重试(软+兜底) > 纯 prompt 文本(软，最不稳)`。任何软约束方案都必须配套 **Pydantic 校验 + 带错误信息的重试**（这正是 instructor 的核心价值）。

### 2.2 墨衍推荐方案（生产主链路：GPT / Claude / DeepSeek 云端 API）

1. **首选 instructor（或自研等价薄层）**：所有"判定 / 出题"调用定义 Pydantic model → `response_model` + `max_retries=2` + `temperature=0` + few-shot 示例。retry 时把 `ValidationError` 信息回喂给模型（instructor 默认行为），2 次仍失败则降级（见下）。
2. **优先用函数调用/Strict json_schema 形态、并把"判定"做成枚举封闭**：`correctness_level` / `decision` 全部用 `enum` + `additionalProperties:false`。枚举越封闭，模型越不容易自由发挥，判定越稳（这也是 JorGPT 5 维打分、PHUDGE rubric、dialogue-kt correctness/KC 标签这类"评分卡式"设计的共同点）。
3. **DeepSeek 专项**（官方文档要点，已抓取）：`json_object` 模式要保证 prompt 含"json"字样 + 给出期望 JSON 示例 + **max_tokens 不要过小**（防截断 → 截断即解析失败，重试也只是浪费 token，建议一次性预留充足 max_tokens）。
4. **线下/本地场景**（未来想省钱或离线）：outlines / lm-format-enforcer 可选；云端主链路别指望它们。
5. **可观测与兜底**：判定 schema 带 `confidence`（模型自评，低置信 → 服务端走保守分支）；
   - 重试耗尽 → 兜底默认分支（如 `practice_question`）+ 打日志 + 人工复核队列；
   - 每次判定落库（judgement JSON 原样存），便于复盘/校准 prompt。
6. 可选：guardrails 做输出门卫（长度、语气、敏感词），但注意不要与 schema 校验重复。

## 三、【判定与反馈模板】两份 JSON Schema 草稿

> 设计依据：dialogue-kt 的"逐轮 correctness + 知识点(KC)标签"、JorGPT 的多维评分卡、PHUDGE 的"rubric + 参考答案为显式输入"、Socratic 式反馈原则（不直接给答案）。两份 schema 可直接作为 Pydantic model 定义（`json_schema` 字段与 Pydantic v2 `model_json_schema()` 兼容）。

### 3.1 Schema ①：学生回答判定（AnswerJudgement）

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "mo-yan/answer-judgement/v1",
  "title": "学生回答判定 AnswerJudgement",
  "type": "object",
  "additionalProperties": false,
  "required": [
    "question_id", "correctness_level", "score",
    "misconceptions", "decision", "weak_points",
    "feedback", "confidence"
  ],
  "properties": {
    "question_id": { "type": "string", "description": "被判定题目的 ID（对应出题模板 question_id）" },

    "correctness_level": {
      "type": "string",
      "enum": ["correct", "partial_correct", "incorrect", "off_topic", "unanswered"],
      "description": "正确性分级：答对 / 部分对 / 答错 / 答非所问 / 未作答。分级由模型判定，但仅限枚举值"
    },

    "score": {
      "type": "number", "minimum": 0, "maximum": 1,
      "description": "归一化得分 0~1，用于累计统计与难度动态调整参考"
    },

    "rubric_scores": {
      "type": "object",
      "additionalProperties": { "type": "number", "minimum": 0, "maximum": 100 },
      "description": "按评分维度细分（参考 JorGPT 5 维打分 / PHUDGE rubric），键为维度名，值为 0~100。可为空"
    },

    "misconceptions": {
      "type": "array",
      "description": "学生的关键误区（答错/部分对时是重点）",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["concept", "description", "evidence"],
        "properties": {
          "concept": { "type": "string", "description": "误区对应的概念/知识点名，应与 weak_points 的 skill_id 对应" },
          "description": { "type": "string", "description": "误区内容：学生错在哪、怎么理解的" },
          "evidence": { "type": "string", "description": "引用学生原话/作答片段作为证据，便于人工复核（可空字符串）" }
        }
      }
    },

    "decision": {
      "type": "string",
      "enum": ["reteach", "alternative_explanation", "practice_question", "skip"],
      "description": "下一步教学动作：①reteach=同一讲法再讲一遍（可能没听懂或没听到）；②alternative_explanation=换一种讲法/换类比；③practice_question=出题巩固（用本次判定的同类点再出一道）；④skip=已掌握，进入下一知识点。decision 只表达意图，具体流转由服务端状态机执行"
    },

    "weak_points": {
      "type": "array",
      "description": "薄弱点标签：写入学生学习档案，后续复习/出题按此检索（与出题模板 knowledge_points 用同一标签体系）",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["skill_id", "mastery", "evidence"],
        "properties": {
          "skill_id": { "type": "string", "description": "知识点/技能标签 ID，如 'algebra/factorization'" },
          "mastery": { "type": "string", "enum": ["low", "mid", "high"], "description": "本次判定体现的掌握度" },
          "evidence": { "type": "string", "description": "判定依据简述（可空字符串）" }
        }
      }
    },

    "feedback": {
      "type": "object",
      "additionalProperties": false,
      "required": ["positive", "correction", "hint"],
      "description": "直接展示给学生的话术（Socratic：给方向不给答案）",
      "properties": {
        "positive": { "type": "string", "description": "肯定与鼓励（1~2 句，先表扬再纠错）" },
        "correction": { "type": "string", "description": "指出错误/误区（不直接给完整答案）" },
        "hint": { "type": "string", "description": "下一步思考提示/引导性问题，把学生引向正确路径" }
      }
    },

    "confidence": {
      "type": "number", "minimum": 0, "maximum": 1,
      "description": "模型对判定的自评置信度；< 0.5 时服务端走保守分支（practice_question + 可人工复核）"
    },

    "generated_at": { "type": "string", "format": "date-time" },
    "model": { "type": "string", "description": "判定所用模型标识（可观测性）" }
  }
}
```

> 落地建议：判定调用建议用 **function calling 形态**——把上述 schema 做成一个 `judge_answer` 工具（`description` 写评分口径：分档定义、Socratic 原则、decision 语义），模型返回 `tool_calls.arguments` 即本 JSON；并配合 Pydantic 校验 + 重试 + `confidence` 兜底。**分值分档口径（例如"partial_correct 的边界：方法对但结果错 / 一步算错"）应写进 prompt 或工具 description，避免跨调用漂移。**

### 3.2 Schema ②：出题模板（QuestionSpec）

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "mo-yan/question-spec/v1",
  "title": "出题模板 QuestionSpec",
  "type": "object",
  "additionalProperties": false,
  "required": [
    "question_type", "stem", "correct_answer",
    "knowledge_points", "difficulty"
  ],
  "properties": {
    "question_id": {
      "type": "string",
      "description": "题目 ID：可由 知识点ID + 序号 生成，保证与判定模板 question_id 相通"
    },

    "subject": { "type": "string", "description": "学科，如 'math'（可选）" },
    "topic": { "type": "string", "description": "章节/主题，如 '二次函数'（可选，便于归档）" },

    "question_type": {
      "type": "string",
      "enum": ["single_choice", "multiple_choice", "true_false", "fill_blank", "short_answer"],
      "description": "题型；墨衍主推 single_choice + short_answer：选择题判定最稳，简答题走 3.1 判定 schema"
    },

    "stem": { "type": "string", "description": "题干（含必要的上下文/素材，若题干过长可引用讲解片段 ID）" },

    "options": {
      "type": "array",
      "description": "选项（选择题必填，其他题型可为空数组）",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["key", "text"],
```

## 四、【状态机建议】教学对话状态流转设计

### 4.1 推荐架构：混合模式 = 服务端状态机 + LLM 输出"判定意图"驱动转移

```
                ┌─────────────────────────────────────────────────────────────┐
                │                  FastAPI 侧服务端状态机                        │
                └─────────────────────────────────────────────────────────────┘

  ┌──────┐   讲解   ┌─────────┐   提问   ┌──────────────┐  学生回答  ┌─────────────┐
  │ INIT │─────────▶│ EXPLAIN │─────────▶│  QUESTION    │───────────▶│ AWAIT_ANSWER│
  └──────┘          │(知识点K) │          │ (题目Q/practice)│           └──────┬──────┘
                    └─────────┘          └──────────────┘                    │
         ▲                  ▲                     ▲                           ▼
         │      换角度/再讲   │                     │        ┌──────────────────────────┐
         │                  │           practice   │        │  EVALUATE：调用 LLM 判定   │
         │                  │           question   │        │  (Schema①：correctness_   │
         └──────────────────┴──────────────────────┴────────│  level + decision + weak  │
                                                      │        │  points)                 │
                                                      │        └────────────┬─────────────┘
                                                      │                     │
    decision=reteach ─────────────▶ EXPLAIN(同K，重讲次数+1)                 │
    decision=alternative_explanation▶ EXPLAIN(K，讲法变体计数+1)◀───────────┤
    decision=practice_question ───▶ QUESTION(由出题模板按 weak_points 生成巩固题)│
    decision=skip ────────────────▶ NEXT_TOPIC（推进，进入下一个知识点K'）──────┘
    判定 confidence<0.5 / 重试耗尽 ─▶ 保守分支 practice_question + 人工复核队列
    学生答非所问(off_topic) ───────▶ QUESTION（提示聚焦后重问，或澄清意图）
```

规则要点：
- **state 是服务端的，不是 LLM 的**：LLM 只输出 schema① 里的 `decision` 意图 + 判定细节；状态转移表（上图的箭头）写死在服务端。这样状态 100% 可审计、可恢复、可重放。
- **连错保护与降难度**：同知识点 `reteach` 连续 ≥2 次 → 强制换 `alternative_explanation`；同知识点连续 3 次判错 → 难度降档（Peblo 的 streak 算法）；连续 3 次对 → 难度升档。
- **薄弱点闭环**：每轮 EVALUATE 的 `weak_points` 聚合写学生档案 → 复习/出题时按 `skill_id` 检索题库（出题模板的 `knowledge_points`）→ 判定模板再评估该 skill → 掌握度变化驱动难度与推进。这就是 dialogue-kt（逐轮 correctness + KC 标签）和 Coding-Tutor（Traver：逐轮验证器 + 知识追踪）在论文里验证过的闭环。
- **对话中途学生插话**：非作答消息（提问、跑题、情绪）→ 服务端先做意图分类（简要 LLM 调用或规则），命中"答疑"则先答再回到当前 state，命中"跑题"则拉回。

### 4.2 实现选型与取舍

| 维度 | 纯 LLM 自由发挥（无状态机） | 服务端状态机 + LLM 判定（推荐） |
|---|---|---|
| 灵活性 | 高，对话自然 | 中，被节点约束 |
| 判定稳定性 | 无保障，同一回答可能给不同结论 | 枚举 + schema + 校验重试，宁可保守也不乱判 |
| 状态可信/可恢复 | 差（上下文丢失即失忆） | 好（LangGraph durable execution / DB 落库可重建） |
| 薄弱点记录 | 靠模型"记得"，不可靠 | 每轮结构化落库，复习系统直接消费 |
| 审计/评估 | 难（开放式对话复盘成本高） | 容易（judgement JSON 全量存档） |
| 开发成本 | 低 | 中（schema + 转移表） |
| 业界佐证 | — | Rasa："The LLM understands the user; the code enforces the rules."（README 原文）；Coding-Tutor 用逐轮 verifier 判定 + 知识追踪，证明"判定驱动"优于自由发挥 |

**实现建议**：
- **起步**：轻量 FSM——`Enum` 状态 + Pydantic 转移表 + `sqlite/postgres` 存 `session_state` 与每轮 `judgement`，FastAPI 内直接实现，零额外依赖、可测、可控。
- **规模/复杂度上来后**：迁到 **LangGraph**（StateGraph 节点/边即上图的转移，自带 durable execution、中断恢复、HITL），仍复用同一套判定 schema。
- 每个教学会话一条 `session` 记录：`{user_id, course_id, current_state, knowledge_path, weak_points_agg, mode_history}`；每轮追加 `turn` 记录：`{session_id, question_id, judge_id, decision, judgement_json}`。
